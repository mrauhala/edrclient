# Bundled schemas

The app validates services and their responses against JSON Schemas it serves itself, from
`public/schemas/`. They are generated by `scripts/download-schemas.js` and committed, so the app
needs no network access to schemas.opengis.net at runtime.

## What is bundled

Service schemas live in `public/schemas/individual/{api}-p{part}-v{version}/`: OGC API standards
have both a part number and a version (EDR Part 1 v1.2, Features Part 2 v1.0), and the directory
names say both. The validator picks the sets that match the conformance classes a service declares.

| Directory | Standard | Files |
|---|---|---|
| `individual/common-p1-v1.0` | OGC API - Common Part 1 v1.0 | landingPage, confClasses |
| `individual/common-p2-v1.0` | OGC API - Common Part 2 v1.0 (draft, from GitHub) | landingPage, confClasses, collections |
| `individual/features-p1-v1.0` | OGC API - Features Part 1 v1.0 | landingPage, collections, confClasses |
| `individual/features-p2-v1.0` | OGC API - Features Part 2 v1.0 (CRS) | collections |
| `individual/edr-p1-v1.0` | OGC API - EDR Part 1 v1.0 | landingPage, collections, confClasses |
| `individual/edr-p1-v1.1` | OGC API - EDR Part 1 v1.1 | landingPage, collections, confClasses |
| `individual/edr-p1-v1.2` | OGC API - EDR Part 1 v1.2 | landingPage, collections, confClasses |
| `individual/records-p1-v1.0` | OGC API - Records Part 1 v1.0 | landingPage, catalogs |
| `individual/maps-p1-v1.0` | OGC API - Maps Part 1 v1.0 | landingPage, collections, confClasses |

Response and document schemas:

| Path | Validates |
|---|---|
| `edr/{1.0,1.1,1.2}/edrFeatureCollectionGeoJSON.json` | EDR locations responses and EDR GeoJSON query results |
| `covjson/1.0/coveragejson.json` | CoverageJSON query results |
| `openapi/{3.0,3.1}/schema.json` | servers' API definitions (OpenAPI documents) |

## Sources

- **schemas.opengis.net:** Features, EDR 1.0 and 1.1, Common Part 1, Records and Maps, as YAML.
  They are converted to JSON and fully dereferenced (`@apidevtools/json-schema-ref-parser`), so
  each file stands alone.
- **EDR 1.2** isn't on schemas.opengis.net yet. Its schemas (`landingPage`, `collections`,
  `confClasses`, `edrFeatureCollectionGeoJSON`) are extracted from `components.schemas` of the
  upstream OpenAPI 3.1 bundle in `opengeospatial/ogcapi-environmental-data-retrieval`.
- **Common Part 2** comes from the draft in `opengeospatial/ogcapi-common` on GitHub.
- **OpenAPI 3.0 and 3.1** come from spec.openapis.org and are used as published (not
  dereferenced: both are recursive), with two small transforms so AJV can run them. The download
  fails if upstream changes what the transforms rely on:
  - **3.0** is a draft-04 schema and AJV runs draft-07 and later: drop `$schema`, rename `id` to
    `$id`, and turn the one draft-04 boolean `exclusiveMinimum` (`Schema.multipleOf`) into the
    numeric form.
  - **3.1:** AJV's `$dynamicRef` support fails every document on the four `"$dynamicRef": "#meta"`
    references. In the base dialect they resolve to `#/$defs/schema`, so they become plain `$ref`s.
    The validator also registers the `media-range` format.
- **CoverageJSON 1.0** is the published `coveragejson.json` (`$id`
  `https://schemas.opengis.net/covjson/1.0/coveragejson.json`); the script doesn't download it.

## Regenerating

```bash
npm run schemas                          # every schema
npm run schemas -- "EDR Part 1 v1.2"     # only entries whose name contains the filter
npm run schemas -- "OpenAPI"
```

Run it from the repository root; it writes into `public/schemas/`. Afterwards run `npm test`: the
OpenAPI structure tests validate real servers' documents against the regenerated schemas.

Three entries are marked `skip` because the committed files carry manual fixes on top of upstream,
and regenerating would lose them (see their git history):

- EDR Part 1 v1.0 and v1.1 collections
- Maps Part 1 v1.0 collections: the UAD extent's `allOf[1]` omits `spatial` and `temporal` from its
  `properties`, so `additionalProperties` misclassified them; they're declared as known properties

To add a standard or version, add an entry to the `schemas` list in `scripts/download-schemas.js`
and a matching set in `SchemaValidator.ts`.
